# 1. OBJECTIF DE CETTE V1

Ajouter un troisième rôle :

```text
USER
```

L’écran de connexion doit maintenant proposer :

```text
[ Administrateur ]

[ Boutique ]

[ Utilisateur ]
```

L’utilisateur normal doit pouvoir :

1. se connecter ;
2. arriver sur son Accueil ;
3. prendre une photo avec son téléphone OU sélectionner une image/capture d’écran depuis sa galerie ;
4. envoyer cette image au backend ;
5. faire analyser l’image par Gemini ;
6. obtenir une description structurée extrêmement précise du produit visible ;
7. comparer cette description aux produits réellement enregistrés par les boutiques ;
8. retrouver les produits les plus similaires ;
9. afficher les boutiques qui possèdent probablement ce produit ;
10. afficher :

* nom de la boutique ;
* adresse exacte ;
* numéro de téléphone ;
* produit correspondant ;
* couleurs ;
* tailles déclarées ;
* stock déclaré ;
* prix si disponible ;
* distance depuis l’utilisateur si la localisation est disponible ;

11. privilégier la boutique la plus proche **parmi les boutiques possédant réellement un produit suffisamment similaire**.

IMPORTANT :

La proximité ne doit JAMAIS permettre à un mauvais produit de dépasser un meilleur produit.

Il faut d’abord déterminer quels produits correspondent suffisamment à la photo.

Ensuite seulement :

trier les boutiques correspondantes par distance.

# 14. IMPORTANT SUR LES PLUSIEURS CLÉS GEMINI

Implémenter proprement un pool de clés.

Mais NE PAS supposer :

```text
5 clés = 5 fois plus de quota
```

Les clés peuvent partager le quota de leur projet.

Le système multi-clés sert principalement à :

* clé invalide ;
* clé désactivée ;
* erreur d’authentification spécifique ;
* résilience ;
* configuration avec plusieurs clés autorisées.

Comportement :

```text
key1
 ↓ erreur exploitable
key2
 ↓
key3
 ↓
...
```

Ne jamais créer une boucle infinie.

Chaque clé doit être essayée au maximum une fois par analyse.

* API key ;
* réponse interne sensible ;

```text
récupérer 20 000 produits
+
envoyer les 20 000 produits à Gemini
+
demander "lequel correspond ?"
```

Ce serait :

* lent ;
* cher ;
* fragile ;
* inutile ;
* difficile à scaler.

Architecture obligatoire :

```text
Gemini
   ↓
extrait un VisualProductProfile
   ↓
Backend
   ↓
compare avec MongoDB
```

Le matching est effectué côté backend.

# 48. SÉLECTION DES MATCHS AVANT DISTANCE

Algorithme recommandé :

```text
bestScore = meilleur score

garder seulement :
score >= MIN_MATCH_SCORE
ET
score >= bestScore - MATCH_WINDOW
```

Exemple :

```text
MIN_MATCH_SCORE = 55
MATCH_WINDOW = 8
```

Si meilleur produit :

```text
91
```

on garde par exemple :

```text
91
88
85
83
```

mais pas :

```text
65
```

simplement parce que sa boutique est proche.

# 106. RÈGLE FINALE

Je veux une **V1 simple à utiliser**, pas une usine à gaz.

Le commerçant doit pouvoir créer un produit rapidement.

La complexité nécessaire à la reconnaissance visuelle doit être principalement gérée automatiquement par :

```text
photo produit
+
Gemini
+
profil visuel structuré
```

et non par :

```text
30 champs obligatoires à remplir manuellement.
```

Le USER doit seulement :

```text
prendre/choisir une image
↓
éventuellement indiquer sa taille
↓
Rechercher
```

Puis l’application lui indique les boutiques réellement présentes dans la base, avec adresse, téléphone et distance lorsque disponible.

COMMENCE MAINTENANT PAR INSPECTER LE PROJET EXISTANT.

NE RECRÉE RIEN QUI FONCTIONNE DÉJÀ.

MODIFIE PROPREMENT LE PROJET ET EXÉCUTE LES TESTS À CHAQUE ÉTAPE.
